PRIVATE FOUNDRY TO TEAMS

We validated the native REST publish path

Using Microsoft's official REST API — the programmatic equivalent of the portal's Publish to Teams button — against the private Foundry project, on throwaway copies so nothing already in production was affected.

HOW WE TESTED IT

  1. IdentityRetrieved each agent's identity and the tenant ID.
  2. Bot ServiceCreated an Azure Bot Service per agent with the Teams channel enabled.
  3. Activity protocolEnabled the agent's activity endpoint and Bot Service authorization.
  4. PublishCalled the Microsoft 365 publish API with Shared scope — returned a Teams app and catalog ID.
  5. Controlled ingressRouted inbound Teams traffic through our public entry point to the private Foundry endpoint. Additive only.

WHAT WE FOUND

✓
Publishing worked

Both agents accepted by the publish API and registered in the Teams / Copilot catalog.

✓
Inbound path verified

Ingress accepts the route and rejects unauthenticated calls — plumbing to the private endpoint is in place.

✓
Search-grounded agent behaves as expected

Standard question-and-answer over indexed content works cleanly.

!
MCP agent hits the known limit

Per-user delegated tool auth and interactive tool consent are not carried through the native path — matches Microsoft's documented behavior.

🔐Tested against copies of the agents (*-restapi) with their own Bot Services. All shared-infrastructure changes were additive — existing published agents were untouched.
Takeaway:Native REST is ideal for standard and search-grounded agents with the smallest footprint. Use the custom bridge when per-user delegated tokens or tool consent are required.
